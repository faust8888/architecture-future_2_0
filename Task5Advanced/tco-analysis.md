# TCO: текущая vs целевая архитектура (горизонт 3 года)

## Методология

**TCO** включает CAPEX/OPEX в упрощённой форме для кейса:

- инфраструктура и облако;
- лицензии ПО;
- сопровождение и поддержка (в т.ч. внешние подрядчики);
- **время аналитиков и инженеров** (стоимость ожидания отчётов и ручных доработок — как правило, доминирующая статья при «тяжёлом» DWH).

Единицы — **условные млн ₽ в год** (или относительные индексы), чтобы сравнить **структуру** затрат. Реальный расчёт требует калькулятора провайдера, ФОТ и налоговой модели.

## Допущения (учебный кейс)

| Допущение | Значение |
|-----------|----------|
| Горизонт | 3 года поэтапной трансформации (как в описании кейса) |
| Объём данных | сотни ТБ; рост источников и событий |
| Текущее состояние | выделенное железо + частично облако; SQL Server 2008 DWH; Camel; Power BI |
| Целевое | облако; lakehouse; управляемый Kafka; доменные команды; Data Mesh пилот → масштабирование |

| Статья | Что включает |
|--------|----------------|
| **Вычисления и хранение** | ВМ, Kubernetes, object storage, кластер брокера, warehouse engines |
| **Лицензии** | BI, ETL-legacy, ОС/БД legacy, security tools |

## Сводная модель TCO (условные единицы в год)

Индекс **100** = суммарный относительный TCO «как есть» в год 1. Цель — показать **сдвиг структуры**, а не точный чек.

### Год 1

| Статья | Текущая архитектура | Целевая (начало перехода) |
|--------|---------------------|---------------------------|
| Инфраструктура | 28 | 22 |
| Лицензии (legacy BI/БД/интеграции) | 22 | 18 |
| Персонал (поддержка DWH + ручная аналитика) | 42 | 38 |
| Миграция / пилоты Data Mesh | 3 | **14** |
| **Итого (индекс)** | **95** | **92** |

В год 1 целевая модель часто **не дешевле**: растут затраты на миграцию и двойное сопровождение.

## Интерпретация для «Будущее 2.0»

1. **Лицензии и legacy DWH**: при отказе от расширения SQL Server 2008 как центра логики и переносе витрин в lakehouse/managed BI доля лицензий падает, но потребует разового CAPEX на миграцию данных и обучение.

2. **Время аналитиков**: ключевая экономия при событийной архитектуре и Data Mesh — меньше очередей на «вытащить данные из DWH», проще переиспользовать **data products** с SLA.

3. **Инфраструктура**: переход в облако даёт перераспределение CAPEX→OPEX и возможность резервировать capacity под пики; стоимость брокера и стриминга компенсируется снижением ночных batch-джобов «на часы».

4. **Регуляторика**: формально не отражена в таблице как сумма; целевая модель с контрактами и lineage снижает **ожидаемые потери** от ошибок отчётности и утечек (учитывать в риск-adjusted TCO отдельно).

---

## Вывод

На горизонте **трёх лет** целевая архитектура при данных допущениях даёт **ниже совокупный TCO** за счёт персонала и лицензий, при этом **год 1** может быть дороже или сопоставим из-за инвестиций в миграцию и платформу. Для инвестиционного комитета полезно представить **график cash-flow по кварталам** и отдельно — KPI time-to-report и downtime отчётности.

# Стратегический роадмап внедрения Data Mesh

Связь с целями бизнеса из кейса: **ускорение time-to-market отчётности**, **масштабирование по продуктам и регионам**, **разделение PHI и аналитической витрины**, **подключение партнёров без раздувания DWH**.

---

## Ключевые роли

| Роль | Ответственность в роадмапе |
|------|----------------------------|
| **Data Product Owner (по домену)** | определяет метрики и SLA витрины/потока; приоритизирует backlog доменного data product; согласует контракты с потребителями |
| **Data Engineer** | проектирует пайплайны, качество данных, деплой в CI/CD; ведёт интеграцию с Schema Registry и топиками |
| **BI-аналитик** | семантический слой, дашборды self-service; работает с опубликованными data products, не «лезет» в сырые PHI-контуры |
| **Platform Engineer / Data Platform Owner** | общие сервисы: каталог, оркестрация, IAM, observability; стандарты golden path |
| **Domain архитектор + комплаенс** | классификация данных, политики экспорта из клиники в Mart |

---

## Этапы и бизнес-цели

### Фаза 0 (мес. 0–3): Фундамент

| Действия | Бизнес-цель |
|----------|-------------|
| Каталог данных, единые идентификаторы доменов, политика PHI | снижение регуляторных рисков |
| Выбор Trial-стека: брокер, lakehouse-пилот, CI/CD для данных | готовность к пилоту |
| Назначение DPO + Data Engineer на пилотный домен | явная ответственность |

### Фаза 1 (мес. 3–9): Пилот Data Mesh

| Действия | Бизнес-цель |
|----------|-------------|
| 1–2 домена (например **финансовые расчёты** и **пациентский поток** в обезличенном срезе) выпускают первый **data product** с контрактом | быстрый выигрыш в time-to-report |
| Self-service BI на пилотной витрине | разгрузка IT и аналитического «царя горы» |
| Обучение BI-аналитиков работе с семантическим слоём | масштабируемость команды |

### Фаза 2 (мес. 9–18): Масштабирование

| Действия | Бизнес-цель |
|----------|-------------|
| Подключение **критических доменов**; потоковые витрины | near-real-time KPI |
| Антикоррупционные слои для Camel/DWH-потребителей | безопасная миграция без «большого взрыва» |
| Шаблон onboarding партнёра (фарма/устройства) через ACL | новые направления без раздувания DWH |

### Фаза 3 (мес. 18–36): Зрелость и оптимизация TCO

| Действия | Бизнес-цель |
|----------|-------------|
| Автоматический lineage, политики доступа как код | аудит и контроль затрат на сопровождение |
| Вывод части legacy отчётности из DWH | снижение лицензий и простоя аналитиков |
| Региональные развёртывания по модели федерации data products | география |

## Связь ролей с этапами

```text
Фаза 0          Фаза 1           Фаза 2              Фаза 3
─────────────────────────────────────────────────────────────
Platform Eng ─── стандарты ─── масштабирование ─── автоматизация
Data Engineer ─ пайплайны ─── streaming ───────── оптимизация cost
DPO ──────────── MVP product ─ SLA доменов ─────── портфель продуктов
BI-analyst ───── семантика ── self-service ─────── governance Mart
```

## Метрики успеха (примеры KPI)

| KPI | Цель |
|-----|------|
| Время подготовки нового регулярного отчёта | −40% к концу года 2 vs базовый год |
| Доля запросов через self-service vs ad-hoc SQL | > 60% к году 2 |
| Число доменов с опубликованным data product | 2 → 8+ за 3 года |
| Инциденты нарушения политики PHI в Mart | 0 критических |

# Задание 3. Целевая архитектура и оценка рисков внедрения

Документ описывает целевое состояние экосистемы «Будущее 2.0» на горизонте **три года**, карту рисков трансформации и план их снижения. Контекст и ограничения взяты из кейса (медицина + финтех + ИИ, легаси DWH/ESB, требования регуляторики, запрет на использование медкарт и исследований в «витрине» самообслуживания).

---

## 1. Целевая архитектура (C4: контейнеры и компоненты)

### 1.1 Принципы целевого ландшафта

- **Доменная автономия**: клиники, финтех, ИИ-сервисы, фарма/оборудование (новые направления) владеют своими сервисами и данными продуктового уровня; общие правила — через платформенные сервисы.
- **Событийная шина как основной контракт**: домены публикуют **бизнес-события** (контракты схем в каталоге); синхронные вызовы — точечно и не как основной паттерн интеграции. **Шина событий (Kafka и аналоги) не заменяет ESB «один к одному»** — она переносит доставку и хранение фактов; маршрутизация, трансформации, ФЛК и оркестрация распределяются по другим компонентам (см. п. 1.4).
- **Аналитика и «витрина»**: данные для BI/self-service поступают из **разрешённых доменных источников** и **агрегированных витрин**; персональные медицинские данные и результаты исследований **не входят** в витрину самообслуживания (отдельный контур клиники с усиленным контролем).
- **Постепенный вывод легаси**: SQL Server 2008 DWH, PowerBuilder и точечные связки через Camel остаются **мостами совместимости** до выделения доменных сервисов и потоков данных.
- **Наблюдаемость и безопасность**: единый IAM, аудит, шифрование, классификация данных; политики доступа на уровне ролей и атрибутов.

### 1.4 Вывод ESB (Apache Camel): куда переезжают обязанности

В текущем ландшафте **ESB на Camel** часто совмещает несколько ролей: транспорт, **маршрутизация**, **трансформации** форматов, **форматно-логический контроль (ФЛК)**, **интеграционная оркестрация** и даже фрагменты **бизнес-логики**. **Kafka (или иная шина событий) закрывает только слой надёжной доставки и буферизации событий** между издателями и подписчиками. Остальное при выводе Camel должно быть **явно переназначено** — иначе логика «остаётся в шине» и снова централизуется в платформе данных или в DWH.

#### Что делает ESB сегодня vs что даёт Kafka

| Роль | ESB (Camel) сегодня | Kafka / event bus | Вывод |
|------|---------------------|-------------------|--------|
| Транспорт, асинхронная доставка | да | да | **Переезд на шину событий** |
| Маршрутизация по правилам (content-based, multicast) | да | нет (только топики/partitions) | **Отдельный слой** (см. ниже) |
| Трансформация XML/JSON, mapping | да | нет | **ACL / stream processing / доменные адаптеры** |
| ФЛК, валидация схем, обязательные поля | да | частично (Schema Registry) | **Контракты + DQ + валидация в домене** |
| Сквозная интеграционная оркестрация (saga, таймеры) | часто | нет | **Process manager / workflow** в домене или платформе |
| Бизнес-правила (скоринг, статусы, лимиты) | часто смешано | нет | **Доменные сервисы** (агрегаты), не в шине |

#### Куда переезжают обязанности (целевое распределение)

| Обязанность ESB | Целевой владелец в архитектуре | Как реализуется |
|-----------------|--------------------------------|-----------------|
| **Маршрутизация** сообщений между системами | **API Gateway / BFF** (синхронные запросы); **доменные сервисы** (публикация в «свои» топики); при необходимости — **лёгкий Integration Router** (отдельный сервис или Kafka Streams только для *технической* маршрутизации, без бизнес-правил) | Правила маршрутизации описываются в коде владельца потока или в конфиге ACL; центральный «все маршруты в одном Camel XML» запрещён для новых интеграций |
| **Трансформации** (форматы, каноническая модель) | **Anti-Corruption Layer (ACL)** на границе домена/партнёра; для аналитики — **оркестрация потоков** (batch/stream) в платформе данных | Легаси-форматы (HL7, старые XML из банка) преобразуются в ACL *до* публикации канонического события; DWH больше не «переваривает всё» |
| **ФЛК** (структура, типы, справочники, обязательность полей) | **Schema Registry + data contracts** на границе топика; **DQ** в пайплайнах платформы; **инварианты агрегата** при записи в домене | Отклонённые сообщения — в **DLQ** с алертом; для Mart — отдельные проверки без PHI |
| **Интеграционная логика** (цепочки «если A, то вызвать B и C», компенсации) | **Оркестратор процесса** в домене-владельце процесса (saga / workflow engine) или явные **реакции на события** в сервисах-подписчиках (choreography) | Не переносить в Kafka; критичные сквозные процессы (например «визит завершён → счёт → уведомление») проектируются как saga с идемпотентными шагами |
| **Бизнес-логика** (лимиты, продуктовые правила, медицинские ограничения) | **Bounded context** соответствующего домена (клиники, финтех, ИИ) | Вынос из маршрутов Camel в сервисы с тестами и версионированием API/событий |
| **Синхронные интеграции** «здесь и сейчас» | **API Gateway + доменные REST/gRPC**; ESB только как **временный мост** к системам без событий | Постепенное сокращение точек входа через Camel |

#### Схема распределения (после вывода Camel)

**Mermaid:** [`diagrams/esb-migration.mmd`](diagrams/esb-migration.mmd)

**Переходный период:** контур **ESB Camel + DWH** остаётся **мостом** только для потоков, которые ещё не переведены на ACL + события. Для каждого маршрута Camel в реестре фиксируется **целевой получатель** обязанностей из таблицы выше и дата вывода.

#### Критерии готовности к отключению маршрута Camel

1. Каноническое событие (или API) опубликовано из **домена-источника**.
2. ФЛК и трансформация выполняются в **ACL или домене**, а не в центральном route.
3. Подписчики **идемпотентны**, есть **DLQ** и мониторинг.
4. Бизнес-правила покрыты **тестами в доменном сервисе**, а не в ESB.

## 2. Карта рисков трансформации

Условные шкалы: **вероятность** и **влияние** — качественные оценки для приоритизации (не точечный расчёт в рублях).

| ID | Категория | Риск | Вероятность | Влияние на бизнес |
|----|-----------|------|-------------|-------------------|
| R1 | Архитектурная | Рост технического долга из-за «двойной записи» (легаси DWH + новая платформа) без чётких границ миграции | Высокая | Высокое |
| R2 | Архитектурная | Дублирование истины данных между доменами и витринами, противоречивая отчётность | Средняя | Высокое |
| R3 | Архитектурная | Недостаточная изоляция PHI: утечка медданных в аналитический контур | Низкая | Высокое |
| R4 | Технологическая | Недоступность или деградация шины событий → сбой цепочек near-real-time | Средняя | Среднее |
| R5 | Технологическая | Нехватка компетенций по стримингу, наблюдаемости, SRE для новой платформы | Высокая | Среднее |
| R6 | Технологическая | Перегруз операционных команд при одновременной миграции DWH и ESB | Средняя | Высокое |
| R7 | Организационная | Сопротивление изменениям у владельцев легаси-процессов и затягивание решений | Средняя | Высокое |
| R8 | Организационная | Размытие ответственности между «доменами» и «платформой» | Высокая | Среднее |
| R9 | Организационная | Недостаток кадров под параллельные продуктовые дорожные карты (клиники, банк, ИИ, новые партнёры) | Средняя | Среднее |
| R10 | Регуляторная / комплаенс | Несоответствие требованиям при работе с финансовыми и медданными в мультиоблаке / георасширении | Средняя | Высокое |
| R11 | Архитектурная | Подмена ESB только Kafka: потеря маршрутизации, ФЛК и оркестрации «между системами», рост «скрытой» логики в DWH или кастомных консьюмерах | Высокая | Высокое |

## 3. План управления рисками

Ниже — **меры по снижению** с указанием доминирующего типа воздействия: **технические (Т)** или **управленческие (У)**.

| Риск | Меры снижения | Т / У |
|------|----------------|-------|
| R1 | Ввести **поэтапный план вывода** легаси: периметр по доменам, критерии «готово к отключению»; архитектурный совет утвержает каждый мост Camel/DWH (**архитектурный runway**) | У + Т |
| R2 | Ввести **доменные data products** с явными владельцами, SLA и версионированием контрактов; единый каталог и lineage; один «золотой» источник на метрику в семантическом слое | Т + У |
| R3 | **Технические контуры**: отдельные проекты/ключи шифрования, ABAC/RBAC, маскирование, DLP; автоматические проверки пайплайнов на запрещённые поля; регулярные аудиты | Т |
| R4 | Кластер шины с **репликацией**, квотами, мониторингом; **DLQ** и идемпотентные консьюмеры; runbook и RTO/RPO для критичных потоков | Т + У |
| R5 | Программа **обучения** и найм; внутренние шаблоны (Golden Path) для пайплайнов; парная работа платформенной и продуктовой команд | У + Т |
| R6 | **Волновая миграция**; лимит параллельных крупных изменений; автоматизация тестов и отката в CI/CD инфраструктуры | У + Т |
| R7 | Прозрачные KPI трансформации, спонсорство на уровне руководства, быстрые **пилоты с измеримым эффектом** | У |
| R8 | RACI для доменов и платформы; **федеративная модель данных** с явными границами ответственности | У |
| R9 | Приоритизация портфеля; партнёрство / аутстафф под некритичные задачи; платформенные сервисы снижают порог входа для доменов | У + Т |
| R10 | Юридический и комплаенс-контур на этапе дизайна; **data residency** по регионам; журналирование и доказуемость доступа | У + Т |
| R11 | **Реестр маршрутов Camel** с колонкой «целевой владелец» (ACL / домен / DQ / saga); запрет новой бизнес-логики в ESB; архитектурный review каждого «просто повесим на Kafka» | У + Т |

### Приоритет первых шагов (согласовано с этапами из кейса)

1. Составить **инвентаризацию маршрутов Camel** (маршрутизация, трансформация, ФЛК, оркестрация, бизнес-правила) и для каждого указать **целевой компонент** по п. 1.4.
2. Определить **границы доменов** и запретить загрузку PHI в контуры витрины самообслуживания (политики + технические проверки).
3. Запустить **пилот событийной интеграции** в 1–2 доменах с каталогом схем, ACL на входе и DLQ (без переноса оркестрации в Kafka).
4. Зафиксировать **единый каталог данных** и lineage для новых потоков; легаси-DWH маркировать как deprecated для новых кейсов.
5. Для новых партнёров — **антикоррупционный слой** и контрактные тесты на события до расширения на критические домены.

# Обоснование событийной архитектуры против связки Camel + DWH

## Текущее состояние (упрощённо)

Интеграции завязаны на **ESB (Camel)** и **центральный DWH на SQL Server 2008**: потоки данных и часть бизнес-правил концентрируются в хранилище, отчётность и кастомизации BI строятся поверх монолитного контура. Это давало контроль на раннем этапе, но при масштабе «Будущего 2.0» (финтех, ИИ, новые регионы и партнёры) становится узким местом.

## Целевой событийный подход

Домены **публикуют факты** (past-tense domain events) в регламентированные топики с версионированными контрактами. Потребители **решают самостоятельно**, какие проекции им нужны (витрины, антифрод, биллинг). Синхронные вызовы и шина Camel допускаются как **исключение** на переходном периоде и для запросов/ответов (не как основной канал распределённой правды).

## Преимущества для «Будущего 2.0»

### 1. Гибкость и скорость изменений

Новое направление (фарма, оборудование) подключается через **ACL и события**, без массовых изменений в центральном DWH и без распределения транзакций через очередь интеграционных заданий Camel. Контракты событий эволюционируют через Schema Registry и совместимость по semver — параллельно можно держать несколько версий потребителей.

### 2. Масштабируемость нагрузки

Запись и чтение разделены: домены масштабируются по своим сервисам; брокер и потребители масштабируются горизонтально. Для near-real-time сценариев (мониторинг платежей, операционные дашборды) поток событий естественнее, чем «очередь тяжёлых преобразований» в одном DWH.

### 3. Автономия команд и границы ответственности

DDD bounded contexts получают **явную модель владения данными**. Истина по кредитному договору живёт в контексте кредитования; Mart только подписывается на разрешённые события — это снижает связность команд и конфликты при релизах.

### 4. Регуляторика и PHI

Медицинские карты и результаты исследований не должны попадать в «витрину» самообслуживания. При событийной модели проще применить **политики на уровне топиков и полей контракта** (маскирование, отдельные защищённые топики, отсутствие запрещённых атрибутов в схемах для Mart). В монолитном DWH исторически выше риск «случайной» утечки полей в общие витрины.

### 5. Наблюдаемость и восстановление

События — естественный журнал для трассировки бизнес-процессов. При сбое потребителя возможны **replay** и перестроение проекций без блокировки операционной записи в домене (при соблюдении идемпотентности).

## Что теряется и как компенсировать

| Риск событийного стиля | Компенсация |
|------------------------|-------------|
| Сложность отладки распределённых цепочек | корреляционные идентификаторы, трассировка, стандарты именования событий |
| Идемпотентность и порядок | ключ партиционирования по агрегату, dedup по `eventId`, outbox/inbox |
| Запрос «общего состояния здесь и сейчас» | CQRS read-модели, материализованные представления, точечные sync API |

## Роль Camel и DWH на переходе

**Camel** остаётся **антикоррупционным маршрутизатором** для систем, которые ещё не говорят на канонических событиях. **DWH** — консьюмер для исторической отчётности и сверки до полного вывода в lakehouse/mart-проекции. Новые возможности компании по возможности **не добавляют бизнес-логики в DWH**, а расширяют поток событий и доменные сервисы.

## Вывод

Для «Будущего 2.0» переход на **интеграцию через доменные события** даёт более предсказуемое масштабирование по продуктам и регионам, ускоряет подключение партнёров и лучше стыкуется с требованиями безопасности медицинских и финансовых данных по сравнению с архитектурой «всё через центральную шину и DWH».
